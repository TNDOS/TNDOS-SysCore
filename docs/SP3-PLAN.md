# SP3 开发计划

**为什么有这份文档**：前面二十几轮是「一轮修上一轮的洞」，代价是同一类问题
反复出现（固件争用出现五次）。这份把剩下的活一次排清楚，**每轮交付一个可验证的东西**，
不是「解决上一轮的问题」。

## 0. 一条贯穿所有驱动的流水线

回头看，每个驱动都走同样四步。**判进度就用这四步，不用感觉。**

```
① 看得见   找到设备、读寄存器、在屏幕上打出来
② 能对话   建「发命令 / 等事件」的最小通路，先用一条无害命令验证
③ 能读     读一块真实数据（AHCI 的扇区、USB 的描述符）
④ 能用     接到内核的框架上（文件系统 / 输入后端 / 控制台）
```

现状：

```
驱动      ①   ②   ③   ④     说明
PCI      ✓   ✓   ✓   ✓     设备表 + 按类归 TND_DEVICE
PS/2     ✓   ✓   ✓   ✗     键鼠都能解码；**④ 差一行 in_register**
AHCI     ✓   ✓   ✓   ✗     读得出扇区（和主机逐字节对上）；未接文件系统
USB      ✓   ✓   ✓   ✓     **完整**：控制器 / 环 / 槽位 / EP0 / 描述符 /
                              SET_CONFIGURATION / 中断 IN 端点 / HID 报告
                              （④ 还差接进内核的输入后端）
显卡     ✓   ✓   ✓   ✗     **自己设模式 + 自己画**（1024x768x32 + 彩条）
                             ④ 待做：控制台改用新参数（现在画花了，是预期的）
NVMe     ✓   ✓   ✓   ✗     **完整**：寄存器 / admin 队列 / IDENTIFY / I-O 队列 / 读 LBA
                             （④ 待做：接文件系统。LBA 格式字段顺序还没核对）
```

## 1. 结构性问题：固件还占着设备

**这是目前最大的浪费源。** 出现的次数：

```
PS/2  固件的 Ps2KeyboardDxe 还在轮询 8042  -> 输入接管只能停在「差一行」
USB   固件的 XhciDxe 还在用同一个端口      -> 五次异常/卡死/事件被顶掉
```

上面的判断：**USB 描述符读不出来，很可能就是它。**
`xhci_address_slot` 会调 `usb_device_reset(dev)` —— 我们重置了固件正在用的设备。
之后两个「槽位」抢一个设备，它的包就不完成了。

### 解法：把设备从固件的驱动手里摘下来

UEFI 的标准做法是 `gBS->DisconnectController()`：

```
1  遍历有 EFI_PCI_IO_PROTOCOL 的 handle
2  用 PciIo->GetLocation() 拿到 segment/bus/device/function
3  匹配上目标设备 -> DisconnectController(handle, NULL, NULL)
   -> 固件挂在这个设备上的驱动被卸掉，之后它不再碰它
```

内核有 `gBS`，这件事只能在内核做（驱动是 TNX，拿不到固件服务）。
所以做成一条 API：**`tnd_pci_own(bus, dev, fun)`** —— 驱动告诉内核「这个设备归我了」。

**注意**：绝对不能对整个系统做这件事。GOP 挂在 00:01.0 上，
把它摘了屏幕就黑了。**只摘驱动自己那个设备。**

## 2. 剩下的活（按依赖顺序）

### A  解开结构性阻塞（1-2 轮）

```
A1  内核加 tnd_pci_own(bus,dev,fun)：LocateHandleBuffer + PciIo->GetLocation
    + DisconnectController。API 表加一项（v2.6）
A2  PS/2 驱动在 attach 里调它，然后 tnd_api()->in_register(&gInput)
A3  验证：敲键盘，字符进到 shell 里（**这是 PS/2 的 ④**）
```

### B  USB HID 收尾（2-3 轮）

```
B1  诊断「为什么没有 Transfer Event」
      先做 A（固件摘掉）再看得不得——很可能 A 一做完这里就通了
      还不行就 -trace enable=usb_* 看包级事件、-d guest_errors 看 QEMU 抱怨
B2  GET_DESCRIPTOR：device(18) -> config(先读 9 字节头部拿 wTotalLength，再读全)
B3  SET_CONFIGURATION(1) -> Configure Endpoint（中断 IN，DCI 3）
B4  轮询中断环读 HID 报告 -> 接输入后端
```

### C  通用显卡（2 轮）

```
C1  Bochs VBE 设模式（Dispi 寄存器；驱动里 dispi_wr 已经有了，只是没用）
    先设成控制器报告支持的模式（现在读到的是 1280x800x32）
C2  让内核控制台切到我们自己设的模式（con_fb 后端改用新参数）
```

### D  NVMe（2 轮）

```
D1  admin queue（ASQ/ACQ）+ 控制器使能 + IDENTIFY，读出型号和 namespace
D2  I/O queue + 读一个 LBA，和 AHCI 一样和主机对字节
```

### E  接进内核（每项 1 轮）

```
E1  AHCI 接文件系统（多一个盘符；用现成的 FAT 代码）
E2  收尾：ROADMAP 勾选、DRIVER-SDK 补一节状态
```

## 3. 防 thrash 的三条硬规则

**这三条是这份计划真正要解决的问题。**

### 规则 1  一轮 = 一个可验证的交付

```
轮开始时先写下两行：
  这轮交付什么（一句话，能被截图/trace 证明）
  怎么验证它
写不出来就别开工 —— 那是「看看能发现什么」，不是一轮。
```

### 规则 2  实验失败就回退，不留半成品

```
实验前写下「什么结果会推翻它」。
跑完若不成立：**回退到本轮开始的状态**，把发现记进文档，再提交。
**永远不要用「反正先提交着」结束一轮** —— 那正是下一轮变成
「修上一轮」的原因。
```

### 规则 3  同一类问题出现两次，就去做结构性修复

```
固件争用出现第一次   打补丁（绕开）
               第二次   打补丁（绕开）
               第三次   打补丁（绕开）
               ...  第五次才想到做 DisconnectController

**第二次就该停手做结构性修复。** 打第三个补丁的成本一定高于修根因。
```

## 4. 每轮收尾必须满足

```
□ 真的构建过（内核 + 受影响的 TNX）
□ 真的在 QEMU 里跑过，读回了证据（截图 / trace / 串口）
□ 仓库干净（所有改动已提交或已回退）
□ 没有推送
□ 若卡住：把「观察到什么、排除了什么」写进 docs，而不是只留在对话里
```
