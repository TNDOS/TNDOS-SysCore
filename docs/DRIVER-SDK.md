> 状态：**设计阶段，没有代码。**

## 0. 先说现状（侦察结论）

```
驱动         是一个 **EFI 应用**（PE），由 drv.c 用固件的 LoadImage + StartImage 拉起来
驱动运行时   repos/TNDOS-SDK/lib/drvlib.c —— **只有 23 行**，全是输出助手
             而它们写的是 EFI_SYSTEM_TABLE->ConOut
内核侧       TND_DRIVER 只是一个**记账结构**（路径、状态、次数）
tnd.h        **没有任何驱动协议类型**
```

**结论：驱动是固件的驱动，不是 TNDDOS 的。**

```
内核把驱动拉起来 -> **然后就不管了**
驱动自己去找固件要 GOP / SimpleTextInput / ...
-> **内核与驱动之间没有接口** ✗
```

**这就是「驱动 SDK 很麻烦」的真正原因** —— 它不是写文档，是**从零定义一层协议**。

---

## 1. 要定义的四件事

```
1  驱动怎么被加载      现在：固件 LoadImage(PE)   目标：内核自己加载 TNX
2  驱动怎么登记自己    现在：没有                 目标：一个明确的入口
3  内核怎么调用驱动    现在：没有                 目标：一套设备接口
4  驱动怎么拿到设备    现在：直接问固件           目标：问内核，或者内核分配
```

**第 3、4 条是核心。** 1、2 条只是把加载路径换掉。

---

## 2. 一个关键取舍：**中断**

现在没有 IDT。所以接口里中断占什么位置，直接决定能不能现在开工：

```
a  接口里没有中断（纯轮询）
   -> 现在就能做 / 简单
   -> 但键盘轮询真的很难受，而且不是长久之计 ✗

b  接口里**留中断的位置，先不实现**
   -> 现在就能做 /
   -> 将来接中断**不用改接口** ✓✓✓

c  接口依赖中断
   -> 必须先做 IDT ✗ 卡住
```

**选 b。** 这和 TNX 的 `SIGN` 段是同一个手法：

> **留位置，不实现。** 位置先占住，实现等需求。

**具体做法**：驱动结构里留中断相关的槽位，但内核侧先只支持「轮询」这一种模式；
驱动可以声明「我希望有中断」，内核如实回答「暂时没有」，驱动退化成轮询。

**驱动必须能接受「没有中断」这个答案** —— 否则它就不是可移植的。

## 3. 驱动长什么样（草案）

### 3.1 加载

```
驱动 = **TNX 文件**，不再走固件 LoadImage
      -> 这是「能不能离开 UEFI」的地基之一
```

**但驱动和普通程序需要区分。** 两种做法：

```
a  用 TNX 的 Flags 位标一个「我是驱动」      -> 要改 TNX 规范 ✗
b  驱动就是一个普通 TNX，**靠它的入口说明自己** -> 不改格式
```

**倾向 b**：包管理器那次的教训 —— **能用魔数或入口解决的事，不要动格式。**

### 3.2 登记 —— 借 EDK II 的形状（已核对源码）

`E:\edk2-edk2-stable202602\MdePkg\Include\Protocol\DriverBinding.h`：

```c
typedef struct _EFI_DRIVER_BINDING_PROTOCOL {
  EFI_DRIVER_BINDING_SUPPORTED  Supported;   /* 这个设备你要不要 */
  EFI_DRIVER_BINDING_START      Start;       /* 要了之后初始化   */
  EFI_DRIVER_BINDING_STOP       Stop;        /* 放开             */
  UINT32        Version;
  EFI_HANDLE    ImageHandle;
  EFI_HANDLE    DriverBindingHandle;
};
```

**三件套描述的是生命周期：要不要 / 初始化 / 放开。** 这个形状直接用。

#### 但真正要学的是 `DriverBindingHandle` 那个字段

```
容易写成的样子：驱动 = 一个跑起来、然后自己去找设备的程序   <- 单例
EDK II 的样子：  驱动 = **一段代码 + 若干「绑定实例」**，每个设备一个
```

**一个驱动可以绑到多个设备上** —— 一个 vga 驱动同时服务两块显卡。

**所以状态必须放在「绑定实例」里，不能放全局变量：**

```
全局变量：分辨率、显存映射、命令队列     <- 两块卡就打架
绑定实例：这些每个设备一份              <- ✓
```

**`DriverBinding` 这个名字本身就是这个意思 —— 驱动被「绑」到设备上。**
这不是 UEFI 的怪癖，是驱动模型该有的样子。

#### 我们的形状（草案）

```
驱动入口      drv_main(api)   -> 注册一个「驱动描述」
驱动描述      名字 / 类型 / supported / start / stop
绑定实例      内核为每个被认领的设备分配一份，驱动往上挂状态
```

**和 EDK II 的差别只有一处**：我们不做 `RemainingDevicePath` 那套
（总线枚举的子设备路径），因为**我们目前没有总线驱动** —— 设备是扁平的。

#### 一个反例：`E:\UEFIDOS`

上一级目录里有一个同名的早期尝试（另一个模型做的）。它只有一个 4.9 KB 的 `boot.c`
和一个 0.2 KB 的空 `kernel.c`，**没有任何驱动模型**。

```
教训 1  README 里写着「如果你希望我现在开始实现…」「请选择下一步」
        —— **AI 的对话输出被直接当交付物存进去了** ✗
教训 2  规范写得很像样，但一行都没实现
        —— **规范不是进度** ✗
```

**我们能拿到的最大教训**：文档和代码分开看。**文档写得再漂亮，也不能算实现过。**

### 3.3 设备从哪来

```
现在   驱动自己去找固件（GOP / SimpleTextInput）
目标   内核把设备描述交给驱动
```

**但设备从哪来？** 这是最深的一层：

```
短期   仍然从固件拿（GOP / 块设备句柄），内核转手给驱动
长期   内核自己枚举 PCI（0xCF8/0xCFC），不再问固件
```

**短期做法能让 SDK 现在就有用**，长期做法才是「脱离 UEFI」的那一步。

## 8. 【重要】一个被限制逼出来的结论

写 PS/2 的时候撞墙了，撞出来的东西比预期重要。

### 8.1 撞墙经过

```
想把 PS/2 写进内核 -> 需要端口 I/O (0x60 / 0x64)
内核是 MS ABI      -> **不能用内联汇编**
于是找 clang 的内建：
    __builtin_ia32_inb       不存在
    __inbyte / __outbyte     编译过、**链接找不到符号**
    _inp / _outp             不认
    -fms-extensions          没用
-> **内核碰不到端口**
```

### 8.2 但正确的答案就在这条限制里

```
内核    MS ABI  -> 不能用内联汇编 -> 碰不到端口
TNX 驱动 SysV   -> **内联汇编可用** ✓（已验证能编能链）
```

**所以「硬件访问只能在驱动里」不是我们的选择，是 ABI 逼出来的。**

### 8.3 而且内核确实不需要端口

认真过了一遍内核将来会碰的东西：

```
PCI 配置空间   -> 用 **ECAM（内存映射）** 绕开端口，q35 支持 ✓
PS/2 / VGA     -> 驱动的事 ✓
定时器         -> 用 TSC，不需要 PIT 的端口 ✓
串口日志       -> 走固件 ✓
-> **内核可以完全不碰端口** ✓
```

### 8.4 结论

```
驱动 **必须**是 TNX 程序，不能编进内核。
-> 驱动接口**绕不过去**了：想验证任何一块硬件，都得先把接口做出来。
```

**这正好是「先写驱动、看它需要什么」的收益** —— 限制把正确的架构逼出来了。

### 8.5 修正后的第一步

```
1  最小驱动接口（内核侧）
     - 驱动表 / 注册
     - 从一个 TNX 驱动里取入口
2  PS/2 写成 TNX 驱动（源码在 SDK 侧，SysV，内联汇编做端口 I/O）
3  内核加载它，加一个 PS2 命令验证敲键有回声
```

**PS/2 仍然是最好的第一个驱动** —— 它不需要 PCI、不需要 MMIO、不需要 DMA，
而且轮询模式下不需要 IDT。它是验证接口的最小用例。

## 9. 驱动住在哪 —— 一个绕不过去的地址模型问题

做驱动模型的时候发现，它卡在比接口更底层的地方。

### 9.1 冲突（查过代码）

```
TNX 只有一个窗口    TNX_IMAGE_BASE = 0x1000000，8 MiB        tnd.h:24
validate 硬校验      ImageBase != 那个值 -> 拒绝              tnx.c:218
**加载前清零**        t_memzero 整个窗口                       tnx.c:360
 pmm 预留窗口        pmm.c:135

驱动走固件           DEVICE= -> drv_load -> LoadImage(PE)     conf.c:101
程序走 TNX           裸程序名 -> tnx_run                      shell.c:217
```

于是：

```
驱动要**常驻**，
但 TNX 加载时会把整个窗口清零 -> **下一个程序一跑，常驻的驱动就没了**
而且 ImageBase 被硬校验成唯一值 -> **驱动根本没有地方住**
```

**所以驱动模型绕不过地址模型。**

### 9.2 答案（只有一个）

TNX 支持**多个固定窗口**：

```
0x1000000   程序窗口   8 MiB   现在这个，**不动**（已有的 TNX 全部继续有效）
0x2000000   驱动窗口   8 MiB   新增
```

改动只有三处：

```
validate    ImageBase 必须是**已登记的窗口之一**（不再是唯一值）
tnx.c:360   清零只清**目标窗口**，不是固定那一个
pmm         多预留一个窗口
```

**格式一行不改** —— `ImageBase` 本来就是字段，只是加载器把限制放宽了。
**所以这不需要升版本**，v1.1 保持不动。

### 9.3 为什么不是别的做法

```
「驱动和程序共用一个窗口」 -> 加载时清零会清掉常驻的驱动 ✗
「驱动放到窗口的后半」     -> 需要窗口内分配器，而程序基址是固定的 ✗
「驱动自己挑基址」         -> 那就需要重定位 ✗ 是 TNX 的反目标
```

**每个窗口一个固定基址，正好保住「无重定位」这一条** ✓

### 9.4 这就是 SDK 要回答的问题

> **「驱动怎么和程序共存」不是格式问题，是加载策略问题。**

驱动常驻、程序临时、两者基址不同 —— 这三件事定了，接口才有地方站。

**顺序也因此定下来**：先多窗口，再驱动接口，最后才是驱动本身。

# 10. 实际做出来的样子

**前面九节是设计。这一节是已经跑起来的东西，以及路上踩过的坑。**

写这一节的理由：设计文档读起来总是顺的，而真正花时间的从来不是设计，
是那些「看起来在正常工作、其实全错」的时刻。那些东西不写下来，
下一个人（包括三个月后的自己）会把同样的弯路再走一遍。

## 10.1 六个驱动各自走到了哪

```
PCI 枚举    OK   全通。7 个设备，和 q35 的真实布局一一对上
PS/2 键盘   OK   能读键。真机上敲字验证过
显卡        部分 找得到设备 + 能读 Bochs VBE 模式寄存器（b0c5 / 1280x800x32）
                 设模式卡在**控制台归属**：GOP 画的就是同一块帧缓冲
AHCI        OK   **读得出扇区**。读回本系统引导扇区，逐字节和主机侧对上
USB         部分 控制器看得见（caplen 40 / v1.0 / 8 ports）
NVMe        部分 控制器看得见（v1.4 / 2048 项 / 门铃步长 4）
                 队列代码**反复触发 #GP**，根因未查明
```

## 10.2 三个被验证过的事实

**一、驱动就是一个 TNX 程序。** 链到驱动窗口，敲名字就能跑，
调 drv_register 登记自己然后返回。**它的窗口不会被清零**，
所以登记的指针一直有效 —— 这就是多窗口的全部意义。

**二、内核碰不到端口，驱动才行。** 内核是 MS ABI，clang 在这个配置下
既不提供 __inbyte，也不让写内联汇编（编译过、链接失败：
error LNK2019: 无法解析的外部符号 __inbyte）。
驱动是 SysV，内联汇编可用。**这不是选择，是 ABI 逼出来的。**

**三、没有分页，虚拟地址就是物理地址。** DMA 直接把指针写进 PRDT / PRP 就行。
这是「没有内存模型」换来的便利。

## 10.3 踩过的坑

按「症状离根因有多远」排序，**越靠前的越值得记**。

### 坑 1：报错的形状会骗你 —— 整块代码插错位置，报的却是「缺声明」

往 nvme.c 里插了 130 行队列代码，**插在了 attach 后面**，而 attach 要用它。
于是编译器报「未声明」：

```
补 nvme_enable   -> 又报 admin_cmd
补 admin_cmd     -> 又报 gId
补 gId，连 QDEPTH 都补了一遍 -> 还是报
```

根因**一次都没变过**，是位置。我却当成「漏了声明」补了四遍。

> **声明报错连着出现两次的时候，该改的是假设，不是补丁。**
> 正确做法：整块挪到 attach 前面 —— **一个声明都不用补**。

### 坑 2：屏幕空白不等于程序在转

驱动「挂死」了四轮。屏幕上除了标题什么都没有，我就以为是死循环，
改了四处、下了两次架。

**而串口日志里第一次就写着：**

```
!!!! X64 Exception Type - 0D(#GP - General Protection) !!!!
```

**没有 IDT 的代价，不只是没有中断，是连「我错在哪」都看不到。**
异常不会告诉你任何事，屏幕上什么都没有，而它其实早就退出了。

### 坑 3：等循环不带失败出口，等于给自己埋一个挂死

AHCI 一开始也等不到（command never started），
但它**有次数上限、会返回、会打印** —— 所以查得下去。

NVMe 那版把上限设成一千万次、一路不吭声，挂在哪一行都不知道。
（顺便：一千万次 MMIO 读大约 25 秒 —— 那不叫等待，那叫卡住。）

### 坑 4：不能假设「数据该在哪」

AHCI 读 LBA 0 拿到全 0，我认定驱动坏了，查了两轮。
实际上 esp.img 前 1 MiB 是空的，文件系统在 **LBA 2048**。
**LBA 0 本来就全是 0。**

> **拿不到预期数据时，先确认「那里到底该有什么」。**

验证就在手边：主机侧读一下 esp.img 的头 16 字节，一条命令的事。
我放到第三轮才做。

### 坑 5：一次只改一个变量

NVMe 的 #GP，前四轮我每次同时改好几样（队列 + 门铃 + 对齐），所以查不出来。
改成「往**能跑的东西**里只加一个变量」之后：

```
只加一个 4KB 静态数组，代码路径一个字没改  -> #GP
只把它从 aligned(4096) 改成 aligned(64)  -> 还是 #GP（假设被推翻）
```

**两次实验就把范围砍掉一半** —— 而且第二次**推翻了我的假设**。
那不是浪费，它把「对齐」从嫌疑名单上划掉了。

### 坑 6：按内容判断，不按名字

DEVICE= 里判断驱动是不是 TNX，**看魔术字，不看扩展名**。
扩展名是给人看的，魔术字才是事实 —— 一个叫 .EFI 的 TNX 也是 TNX。

### 坑 7：大类不够，要看子类

USB 的 probe 一开始只看大类 0x0C（串行总线）。
**而 SMBus 也是 0x0C**（0x0C05）。结果把主板的 SMBus 也认领了，
对着它的 BAR0 读 xHCI 寄存器，读到一堆 0。**USB 是 0x0C03。**

同类：AHCI 只认 TND_DRV_BLOCK 会把 NVMe（0x0108）也认领。
SATA = 0x0106，NVM = 0x0108。

### 坑 8：非对齐的 MMIO 读

xHCI 的 HCVERSION 在偏移 0x02，我用 u32 读 —— 非对齐的 MMIO 访问，
读回来是错的（version 打到 0.0，实际是 1.0）。
**在 0x00 读一个对齐的 u32，再取高 16 位。**

### 坑 9：不能只看 BAR0

AHCI 的寄存器基址是 **BAR5**，显卡的模式寄存器在 **BAR2**，帧缓冲才在 BAR0。
TND_DEVICE 因此带**六个 BAR**。
（而且 64 位 BAR 占两个槽，高半必须一起读，否则地址只剩低 32 位 ——
这种 bug 只在 4GB 以上的机器上才露头。）

### 坑 10：位置初始化的静默错位

TND_DEVICE 加了 Class 字段之后，drv.c 里那行位置初始化静默错位了，
报的错是 "PS2" 被塞进 u32 字段 —— **跟真正的原因隔着十万八千里**。
改用**指定初始化**。

### 坑 11：编译通过不等于能链接

__inbyte 编译过了，链接时找不到符号。
**验证「能不能用」要走到它真的用起来为止。**

### 坑 12：PowerShell 变量名不区分大小写

build-tnx.ps1 加了参数 $Base，被循环里的 $base（取文件名用的）覆盖掉了，
症状是 --defsym=TNX_BASE=drvtest 这种看不懂的东西。
**把命令打出来**是最快的诊断手段。

## 10.4 还没做成的：NVMe 的 #GP

**诚实记下来，因为它推翻了我两个假设。**

```
现象  加载 nvme.tnx -> 打印标题 -> X64 Exception 0D (#GP) -> 系统僵住
位置  在 attach 的第一次打印之前（标题打了，BAR0 没打）
```

已排除：

```
x 对齐      只加 aligned(4096) 的数组 -> #GP
            改成 aligned(64)         -> 还是 #GP
            （AHCI 用 aligned(1024)/aligned(256) 都正常）

x 映像大小  出事的 11976 / 16392
            但 AHCI 是 12808、**能跑**

x BSS 体积  **对照实验**：把同一个 4KB 静态数组（同样 64 对齐）
            放进 USB 驱动 -> imageSize 11784，**完全正常**
              [usb] probe addr = 0x0000000002001E00
              [usb] probe rw ok (a5 5a)
            两个映像几乎一样大、探针一模一样、都在驱动窗口 0x2000000、
            都走 TNX 加载器 —— 一个挂、一个正常。
```

**所以问题在 NVMe 那个文件内部**，不是「加 BSS 会挂」「超过某大小会挂」。
范围还能再收一层：**连 attach 的第一行 BAR0 都没打出来**（驱动的标题打了），
所以 #GP 发生在 **attach 被调用之前**，或者就在 drv_scan 遍历到它的那一刻。

### 第四步：把 drv_register 那一行注释掉

```
C:\EFI\TNDOS>nvme.tnx
  NVMe -- find the controller ourselves
  (registration skipped on purpose -- see the comment)
C:\EFI\TNDOS>            <- **提示符正常回来了**
```

**不登记就一切正常。** 驱动映像加载、tnx_main 运行、退出 —— 全都没问题。

```
驱动映像加载    正常
tnx_main 运行   正常
drv_register    **挂在这里**
```

**范围现在只剩两件事**（drv_register 的全部工作）：

```
1  把描述符存进表        内核侧几个赋值，读 d->Name / StructSize / Type
2  drv_scan()            **会跨 ABI 回调驱动里的 probe 和 attach**
```

### 第五步：把内核里那一次 drv_scan() 调用注释掉

```
[log] cmd: nvme.tnx
[log] drv: registered "NVME"  type=3  total=1     <- 登记成功，没挂
屏幕：drv_register : 0  然后**提示符正常回来**
```

```
存描述符      正常
drv_scan()    **挂在这里**
```

**drv_scan 做的就三件事**，范围已经小到能一眼看完：

```
遍历设备  ->  调 probe  ->  调 attach
            （跨 ABI 回调，进驱动窗口）
```

### 第六步：反汇编两版 probe，再划掉两个

三组对照把范围收到「纯函数 vs 有副作用」。接下来这一步是**把它翻译成具体东西**：

**划掉一：头文件布局分歧**

```
内核 src/include/tnd_api.h      SHA256 34DE760E0425E0E5...
驱动 repos/TNDOS-SDK/include/... SHA256 34DE760E0425E0E5...
-> **逐字节一致**
```

内核和驱动对 `TND_DEVICE` 的布局没有分歧，驱动读到的不是垃圾。

**划掉二：「用不用栈」**

反汇编两版的 `probe` 开头：

```
A（纯函数）                 C（有副作用）
  pushq %rbp                  pushq %rbp
  movq  %rsp,%rbp             movq  %rsp,%rbp
  subq  $0x10,%rsp            subq  $0x10,%rsp
  movq  %rdi,-0x8(%rbp)       movq  %rdi,-0x8(%rbp)
  movq  -0x8(%rbp),%rcx       movl  0x2001df0,%eax     <- 只多这 4 行
  xorl  %eax,%eax             addl  $0x1,%eax
  cmpl  $0x3,0x4(%rcx)        movl  %eax,0x2001df0
                              movq  -0x8(%rbp),%rcx
                              xorl  %eax,%eax
                              cmpl  $0x3,0x4(%rcx)
```

**两版都用栈，栈帧一模一样。** 所以「纯函数不用栈、有副作用用栈、而用栈会挂」
这个假设也被推翻了。

**现在范围是**：两版唯一的差别就是那 4 行 —— 一次对 `imageBase + 0x1DF0` 的
读-改-写（写 `.bss`）。**为什么一次 .bss 写入能决定整个驱动挂不挂，
还没解释清楚。**

顺带记一个反复踩的坑：**我用脚本改文件再写回时加了 BOM**，
导致 git 显示文件被改动、而 diff 只有第一行的 BOM 差异。
还原要用 `git checkout --` 直接回到 HEAD，别自己写回。

### 第七步：验跨 ABI 本身

范围收到「跨 ABI 回调里写内存」之后，最自然的假设是
**clang 在 MS target 上忽略了 `sysv_abi`** —— 那内核就会按 MS ABI 去调
SysV 函数。用一个六行程序直接问它：

```c
__attribute__((sysv_abi)) int sysv_fn(int x, int y);
int ms_fn(int x, int y);
int call_sysv(int v) { return sysv_fn(v, v + 1); }
int call_ms(int v)   { return ms_fn(v, v + 1); }
```

`-target x86_64-pc-windows-msvc` 编出来：

```
call_sysv:
   48:  leal 0x1(%rcx), %esi    读自己的参数（MS ABI：ecx）
   4b:  movl %ecx, %edi         然后摆成 edi
   4d:  callq ...
call_ms:
   a0:  leal 0x1(%rcx), %edx     MS ABI：edx
```

**clang 尊重 `sysv_abi`** —— 它确实把参数搬进了 `edi`/`esi`。
`-target x86_64-unknown-none` 那边参数本来就在 `rdi`，不需要搬运。
**两边一致，所以 ABI 不是原因。**

（这个测试不用跑 QEMU，六行就够 —— 值得记住：**假设可以直接问编译器，
不用每次都上虚拟机。**）

### 五次减法的小结

```
1  aligned(4096) -> aligned(64)     划掉「对齐」
2  同一个探针放进 USB 驱动           划掉「映像大小」+「BSS 体积」
3  注释掉 drv_register 调用          划掉「映像加载」+「驱动主体」
4  注释掉内核里的 drv_scan 调用      划掉「存描述符」，锁定 drv_scan
```

**每一次只改一个变量，每一次都真的跑起来看结果。**
前四轮我同时改三样，四轮下来什么也没排除掉 —— 这就是区别。
而且第 1 次和第 2 次都**推翻了我自己的假设**，那不是白做：
假设被推翻，本身就是缩小范围。

### 第七到第十次排除之后：一条新的线索

后来又排除了：

```
7   两份 tnd_api.h 逐字节一致        -> 结构体布局分歧，排除
8   两版 probe 反汇编，栈帧一模一样  -> 「用不用栈」，排除
9   在 tnx_main 里先碰同一段内存     -> 「那段内存有问题」，排除
      收到：**跨 ABI 回调里写内存**
10  六行程序问 clang 的 sysv_abi     -> 直接函数声明，被尊重，排除
11  结构体成员上的 sysv_abi          -> **也被尊重**（参数进 edi/esi），排除
```

**第 11 步的结论重要**：`TND_DRIVER_DESC` 里那种函数指针成员，
`__attribute__((sysv_abi))` 也是生效的。所以不是「ABI 没对上」。

**而且顺手查到一块编译器薄弱区**：clang 的 PR #138935（"Handle CC attrs for UEFI"）
之前把 UEFI target 下的 `sysv_abi` **降级成 warning 而不报错** ——
也就是说这个组合出问题时**编译器不会拦你**。

### 剩下的唯一线索：栈对齐

```
MS ABI   要求调用时 %rsp **32 字节**对齐
SysV ABI 只要求          **16 字节**对齐

跨 ABI 互调时这是最经典的坑。而被调函数如果用了 SSE 的对齐指令
（movaps 之类，要求 16 字节），栈没对齐就会 **#GP**。
```

**它正好能解释那个怪现象**：纯函数不用 SSE，有副作用的函数编译器会用。
**下一个实验**：在 probe 入口读一次 `%rsp`，看对齐 —— 这是唯一还没看过的寄存器。

> 现在任何异常都会让系统静默僵住。加一个最小的异常处理
> （IDT + #GP/#PF/#UD 桩 + 打印异常号和出错地址），
> 代价很小，收益是**以后这类问题是一条日志，而不是五轮摸索**。

## 10.4b 第二个卡点：xHCI 的四个寄存器写不进去

**和 NVMe 那个并列记在这里 —— 两个都卡在「软件和控制器/ABI 的边界」上。**

现象非常干净：

```
能写进去的   DCBAAP(op+0x18) ✓   ERSTBA(op+0x30) ✓
读回 0 的    CRCR(op+0x10) ✗   CONFIG(op+0x20) ✗
             ERSTSZ(op+0x28) ✗  ERDP(op+0x38) ✗
全程         HCH=1  CNR=0        （写条件满足）
```

前后五次假设，**全部被实验推翻**：

```
1  顺序反了（ERSTSZ 应在 ERSTBA 之前）  改了还是 0
2  写条件不满足（HCH=0 / CNR=1）        全程 HCH=1 CNR=0
3  op = base + caplen 算错              那两个能写的就不该能写
4  地址没按 PAGESIZE 对齐               改成 4KB 还是 0
5  控制器把写忽略了                     2 已经说明条件满足
```

**到这里就不该再试了。** 排除法把范围收得很窄，但再窄也跨不过
「我不知道这一条规则」这一步 —— 下一步是去查规范。**瞎试只会烧掉轮次。**

### 查到了：ERSTSZ / ERSTBA / ERDP 在 Runtime 区，不在 Operational 区

**一次搜索就出答案。**命中两条关键信息：

```
1  Renesas 数据表的表头：
   ERSTSZ Register (Offset Address: **Runtime Base (600h)** + 028h + (20h x Interrupter))
2  SLOF 的一个提交标题：
   usb-xhci: **Reset ERSTSZ together with ERSTBA**
```

xHCI 的寄存器分三块，**我一直只用了前两块**：

```
能力区    base + 0x00 ..          CAPLENGTH / HCSPARAMS / HCCPARAMS
                                 偏移 0x18 = **RTSOFF（运行时区偏移）**
运行时区  base + CAPLENGTH ..     USBCMD / USBSTS / CRCR(0x10) / DCBAAP(0x18) / CONFIG(0x20)
运行时2   base + RTSOFF + 0x20    Interrupter 0:
                                    +0x08 ERSTSZ
                                    +0x10 ERSTBA
                                    +0x18 ERDP
```

**我用 `base + caplen` 去读写后三个 —— 那里根本没有寄存器。**于是：

```
DCBAAP  op+0x18   真的寄存器     -> 写进去、读回对
ERSTBA  op+0x30   **不是寄存器** -> 但那是 MMIO 空间，写进去照样读得回
                                   **所以「写成功」是假象**
ERSTSZ  不是寄存器 -> 读回 0
ERDP    不是寄存器 -> 读回 0
```

**五个假设为什么全都不成立：地址本身就是错的。**和顺序、对齐、
写条件都无关 —— 那些假设都在同一个错的前提上做推理。

**这一轮的价值：一次搜索，胜过五轮试错。**
上一轮判断「该查规范」是对的，这一轮执行了它。

（`CRCR`(0x10) 和 `CONFIG`(0x20) 的偏移在 op 区是对的，它们读回 0
还有别的原因，留到下一轮。另外记下：**ERSTSZ 和 ERSTBA 要一起复位**。）

### 这两个卡点的共同点

```
NVMe  跨 ABI 回调里写内存      -> #GP
USB   写控制器会维护的寄存器    -> 读回 0

两个都发生在**软件和控制器/ABI 的交界处**
两个都是「条件看起来满足，但结果不对」
两个都已经排除了五到十个假设，**范围很窄，缺的是规范细节**
```

**这不是"再努力一点就能突破"的类型。** 认清这一点，
比再试第六个假设有价值。
