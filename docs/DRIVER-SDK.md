# 驱动 SDK —— 接口设计（草案）

> 状态：**设计阶段，没有代码。**
> 先把接口定下来，再谈实现 —— 标准先行，代码才好写。

---

## 0. 先说现状（侦察结论）

```
驱动         是一个 **EFI 应用**（PE），由 drv.c 用固件的 LoadImage + StartImage 拉起来
驱动运行时   repos/TNDOS-SDK/lib/drvlib.c —— **只有 23 行**，全是输出助手
             而它们写的是 EFI_SYSTEM_TABLE->ConOut
内核侧       TND_DRIVER 只是一个**记账结构**（路径、状态、次数）
tnd.h        **没有任何驱动协议类型**
```

**结论：驱动是固件的驱动，不是 TNDDOS 的。**

```
内核把驱动拉起来 -> **然后就不管了**
驱动自己去找固件要 GOP / SimpleTextInput / ...
-> **内核与驱动之间没有接口** ✗
```

**这就是「驱动 SDK 很麻烦」的真正原因** —— 它不是写文档，是**从零定义一层协议**。

---

## 1. 要定义的四件事

```
1  驱动怎么被加载      现在：固件 LoadImage(PE)   目标：内核自己加载 TNX
2  驱动怎么登记自己    现在：没有                 目标：一个明确的入口
3  内核怎么调用驱动    现在：没有                 目标：一套设备接口
4  驱动怎么拿到设备    现在：直接问固件           目标：问内核，或者内核分配
```

**第 3、4 条是核心。** 1、2 条只是把加载路径换掉。

---

## 2. 一个关键取舍：**中断**

现在没有 IDT。所以接口里中断占什么位置，直接决定能不能现在开工：

```
a  接口里没有中断（纯轮询）
   -> 现在就能做 / 简单
   -> 但键盘轮询真的很难受，而且不是长久之计 ✗

b  接口里**留中断的位置，先不实现**
   -> 现在就能做 /
   -> 将来接中断**不用改接口** ✓✓✓

c  接口依赖中断
   -> 必须先做 IDT ✗ 卡住
```

**选 b。** 这和 TNX 的 `SIGN` 段是同一个手法：

> **留位置，不实现。** 位置先占住，实现等需求。

**具体做法**：驱动结构里留中断相关的槽位，但内核侧先只支持「轮询」这一种模式；
驱动可以声明「我希望有中断」，内核如实回答「暂时没有」，驱动退化成轮询。

**驱动必须能接受「没有中断」这个答案** —— 否则它就不是可移植的。

## 3. 驱动长什么样（草案）

### 3.1 加载

```
驱动 = **TNX 文件**，不再走固件 LoadImage
      -> 这是「能不能离开 UEFI」的地基之一
```

**但驱动和普通程序需要区分。** 两种做法：

```
a  用 TNX 的 Flags 位标一个「我是驱动」      -> 要改 TNX 规范 ✗
b  驱动就是一个普通 TNX，**靠它的入口说明自己** -> 不改格式
```

**倾向 b**：包管理器那次的教训 —— **能用魔数或入口解决的事，不要动格式。**

### 3.2 登记 —— 借 EDK II 的形状（已核对源码）

`E:\edk2-edk2-stable202602\MdePkg\Include\Protocol\DriverBinding.h`：

```c
typedef struct _EFI_DRIVER_BINDING_PROTOCOL {
  EFI_DRIVER_BINDING_SUPPORTED  Supported;   /* 这个设备你要不要 */
  EFI_DRIVER_BINDING_START      Start;       /* 要了之后初始化   */
  EFI_DRIVER_BINDING_STOP       Stop;        /* 放开             */
  UINT32        Version;
  EFI_HANDLE    ImageHandle;
  EFI_HANDLE    DriverBindingHandle;
};
```

**三件套描述的是生命周期：要不要 / 初始化 / 放开。** 这个形状直接用。

#### 但真正要学的是 `DriverBindingHandle` 那个字段

```
容易写成的样子：驱动 = 一个跑起来、然后自己去找设备的程序   <- 单例
EDK II 的样子：  驱动 = **一段代码 + 若干「绑定实例」**，每个设备一个
```

**一个驱动可以绑到多个设备上** —— 一个 vga 驱动同时服务两块显卡。

**所以状态必须放在「绑定实例」里，不能放全局变量：**

```
全局变量：分辨率、显存映射、命令队列     <- 两块卡就打架
绑定实例：这些每个设备一份              <- ✓
```

**`DriverBinding` 这个名字本身就是这个意思 —— 驱动被「绑」到设备上。**
这不是 UEFI 的怪癖，是驱动模型该有的样子。

#### 我们的形状（草案）

```
驱动入口      drv_main(api)   -> 注册一个「驱动描述」
驱动描述      名字 / 类型 / supported / start / stop
绑定实例      内核为每个被认领的设备分配一份，驱动往上挂状态
```

**和 EDK II 的差别只有一处**：我们不做 `RemainingDevicePath` 那套
（总线枚举的子设备路径），因为**我们目前没有总线驱动** —— 设备是扁平的。

#### 一个反例：`E:\UEFIDOS`

上一级目录里有一个同名的早期尝试（另一个模型做的）。它只有一个 4.9 KB 的 `boot.c`
和一个 0.2 KB 的空 `kernel.c`，**没有任何驱动模型**。

```
教训 1  README 里写着「如果你希望我现在开始实现…」「请选择下一步」
        —— **AI 的对话输出被直接当交付物存进去了** ✗
教训 2  规范写得很像样，但一行都没实现
        —— **规范不是进度** ✗
```

**我们能拿到的最大教训**：文档和代码分开看。**文档写得再漂亮，也不能算实现过。**

### 3.3 设备从哪来

```
现在   驱动自己去找固件（GOP / SimpleTextInput）
目标   内核把设备描述交给驱动
```

**但设备从哪来？** 这是最深的一层：

```
短期   仍然从固件拿（GOP / 块设备句柄），内核转手给驱动
长期   内核自己枚举 PCI（0xCF8/0xCFC），不再问固件
```

**短期做法能让 SDK 现在就有用**，长期做法才是「脱离 UEFI」的那一步。

## 8. 【重要】一个被限制逼出来的结论

写 PS/2 的时候撞墙了，撞出来的东西比预期重要。

### 8.1 撞墙经过

```
想把 PS/2 写进内核 -> 需要端口 I/O (0x60 / 0x64)
内核是 MS ABI      -> **不能用内联汇编**
于是找 clang 的内建：
    __builtin_ia32_inb       不存在
    __inbyte / __outbyte     编译过、**链接找不到符号**
    _inp / _outp             不认
    -fms-extensions          没用
-> **内核碰不到端口**
```

### 8.2 但正确的答案就在这条限制里

```
内核    MS ABI  -> 不能用内联汇编 -> 碰不到端口
TNX 驱动 SysV   -> **内联汇编可用** ✓（已验证能编能链）
```

**所以「硬件访问只能在驱动里」不是我们的选择，是 ABI 逼出来的。**

### 8.3 而且内核确实不需要端口

认真过了一遍内核将来会碰的东西：

```
PCI 配置空间   -> 用 **ECAM（内存映射）** 绕开端口，q35 支持 ✓
PS/2 / VGA     -> 驱动的事 ✓
定时器         -> 用 TSC，不需要 PIT 的端口 ✓
串口日志       -> 走固件 ✓
-> **内核可以完全不碰端口** ✓
```

### 8.4 结论

```
驱动 **必须**是 TNX 程序，不能编进内核。
-> 驱动接口**绕不过去**了：想验证任何一块硬件，都得先把接口做出来。
```

**这正好是「先写驱动、看它需要什么」的收益** —— 限制把正确的架构逼出来了。

### 8.5 修正后的第一步

```
1  最小驱动接口（内核侧）
     - 驱动表 / 注册
     - 从一个 TNX 驱动里取入口
2  PS/2 写成 TNX 驱动（源码在 SDK 侧，SysV，内联汇编做端口 I/O）
3  内核加载它，加一个 PS2 命令验证敲键有回声
```

**PS/2 仍然是最好的第一个驱动** —— 它不需要 PCI、不需要 MMIO、不需要 DMA，
而且轮询模式下不需要 IDT。它是验证接口的最小用例。
